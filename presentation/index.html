03 / How

OAuth 不只是串接 API，還需要建立 App 與申請審核

原本以為請 Codex 改成 OAuth 就能完成授權，實際操作才發現，還需要到 Figma Developers 完成一系列設定。

申請流程
01
建立 Developer App

在 Figma Developers 建立應用程式，取得串接所需的應用程式資訊。

02
設定 OAuth 權限

選擇平台需要的存取範圍（Scopes），避免要求不必要的權限。

03
設定授權回呼網址

設定 Redirect URI，讓使用者完成 Figma 授權後能返回平台。

04
提交審核

依 Figma 的要求提供應用程式資訊，提交審核並等待結果。

Codex 能協助完成 OAuth 串接程式，但第三方平台的設定、權限與審核流程，仍需要實際處理。

03 / How

OAuth 成功後，但還是遇到 API 額度限制？

雖然已經可以正常讀取設計稿，但不同使用者能呼叫 API 的次數，可能有很大的差異。

01
帳號權限

Viewer、Collab、Dev、Full 等不同席次，會影響 API 使用額度。

02
Figma 帳號方案

Starter、Professional、Organization、Enterprise 等方案，適用的額度可能不同。

03
API 類型

讀取完整設計稿、圖片或檔案資訊，不同 API 的請求限制也不同。

OAuth≠無限額度 除了授權成功，也要考慮請求量。

為什麼我的平台會這麼快用完 Figma API 額度？

原本每次點擊「AI 分析」，都會重新向 Figma 取得設計資料，即使設計稿完全沒有改變，也會消耗 API 額度。

BEFORE / 原本流程
點擊「AI 分析」
重新呼叫 Figma API
AI 產生埋點建議
0次 Figma 請求（分析階段）

問題：同一份設計稿重複分析，會產生不必要的 API 請求。

AFTER / 優化方向 · 使用有效快取
點擊「AI 分析」
優先使用已取得的設計資料
AI 重新產生埋點建議
0次 Figma 請求（分析階段）

改善：減少重複請求，把 API 額度留給真正需要更新的資料。

AI 可以重新分析，但 Figma 資料不一定需要重新讀取。

開始理解代碼背後的運作邏輯
