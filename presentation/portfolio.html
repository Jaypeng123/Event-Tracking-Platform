00 / Overview

專案摘要

PROBLEM

埋點規劃仰賴經驗。用 ChatGPT 協助時，結果散落在對話與 Excel 之間，需要反覆確認、跨工具切換與人工整併。

SOLUTION

以「專案 → Figma Page → 事件」為核心的規劃平台：AI 產出候選事件，設計師審核編輯，最後統一匯出。

MY ROLE

從需求定義、介面設計，到與 Codex 協作開發、串接 Figma 與 AI、部署上線，獨立完成整個產品。

OUTCOME

把 5 段跨工具的手動流程，整合為單一平台的連續操作；每筆事件包含 13 個欄位，可直接交付工程實作。

01 / Context

專案需要規劃埋點，但團隊缺乏經驗

專案正在討論埋點，我先嘗試與 AI 協作撰寫埋點 PRD，才發現寫出有價值的埋點非常仰賴經驗，而且就算有 AI 幫忙，整個流程依然繁瑣。

原本的工作流程
STEP 01
建立 Excel 範本

先定義埋點事件、欄位與填寫規則。

STEP 02
提供 Figma 畫面

將設計稿與分析範圍提供給 ChatGPT。

耗時STEP 03
反覆確認結果

檢查 AI 分析是否正確，持續補充需求與修正。

STEP 04
匯出埋點文件

將分析結果下載成 Excel 檔案。

耗時STEP 05
手動整併版本

合併不同批次的分析結果，整理成最終版本。

真正耗時的不是 AI 分析，而是反覆確認、跨工具切換與人工整併結果。
三個重複成本
需求表達門檻

要會描述畫面、埋點條件與輸出格式，才容易得到可用的結果。

反覆查找與修改

在 ChatGPT 裡反覆修改，對話越長越難回頭找；不同 Page、不同專案的結果也很難整理。

反覆整併 Excel 耗時

不同頁面產出的埋點資料，需要人工合併、檢查與修正，也不容易管理最新版本。

設計機會：把「一次性的 AI 回答」，變成「可編輯、可管理、可交付的文件」。

04 / Key Decisions

五個關鍵設計決策

開發過程中最有價值的，不是畫面順利產出的時刻，而是系統沒有照預期運作、需要重新做判斷的時候。

01
產品通用化
需求寫得太具體，反而限制了產品
問題
一開始把醫療專案的情境直接寫進需求，AI 分不清「產品規則」與「專案範例」。換成電商專案測試時，埋點建議裡竟混入醫療相關事件。
決策
先定義產品通用的欄位、流程與驗收條件，把特定專案降級為測試資料，並將專案內容去識別化。
結果
分析規則改為只根據本次選定 Page 的來源節點，不預設產業、不沿用其他專案，平台得以套用到不同類型的產品。
PRD 階段產出的範例事件CDM_001 · view_page
頁面
個案詳情
觸發條件
當醫療人員進入個案詳情頁，且主要內容載入完成時
追蹤目的
確認個案詳情是否為醫療人員日常查看病患資料的主要入口
TEST電商專案的建議中，出現「病患資訊點擊率」
02
資料真實性
介面有結果，不代表功能已完成
問題
初版看起來功能完整，實際操作才發現沒有串接 AI，分析結果是寫死的示意資料；Page 選擇與空狀態也不完整。
決策
建立完整的資料流：從 Figma 取得節點、整理成模型輸入，再把 AI 回傳解析成標準欄位，最後交給人工審核。同時支援 OpenAI 與 Gemini 模型。
結果
驗證的重點從「AI 有沒有回應」，轉為「模型實際讀到了哪些設計資訊」，每一段資料都能追溯。

03
授權設計
從個人 Token 到 OAuth：讓每位使用者授權自己的 Figma
問題
初期平台用我的個人 Token（PAT）讀取設計稿：所有人共用我的權限，也有共用金鑰的安全與維護風險，無法開放給其他設計師使用。
決策
改用 Figma OAuth，並在 Figma Developers 建立 App、只申請必要的讀取權限，設定授權後的返回網址與發布方式。
結果
每位使用者依自己的權限存取設計檔，從「只有我能用的工具」變成「其他設計師也能用的產品」。
01建立 Developer App
建立 Developer App

在 Figma Developers 建立應用程式，取得串接資訊。

設定 OAuth 權限

只申請必要的存取範圍（Scopes）。

設定授權後的返回網址

使用者按下「允許存取」後，帶回平台。

選擇發布方式

Private App 可直接發布；Public App 須提交 Figma 官方審核。

04
效能與成本
OAuth 成功了，卻還是遇到 Figma API 額度限制
問題
每次點「AI 分析」都會重新向 Figma 抓一次設計資料，即使設計稿沒改也會消耗額度；而額度又受帳號席次、方案與 API 類型影響。
決策
把「取得設計資料」與「執行 AI 分析」分開：第一次匯入後，若快取仍有效，就直接用已取得的資料重新分析。
結果
同一個 Page 反覆分析時，不必再額外讀取 Figma，把額度留給真正需要更新的資料。（優化方向）
BEFORE · 每次都重抓
點擊「AI 分析」
重新呼叫 Figma API
AI 產生埋點建議
0次 Figma 請求（分析階段）
AFTER · 使用有效快取
點擊「AI 分析」
優先使用已取得的設計資料
AI 重新產生埋點建議
0次 Figma 請求（分析階段）
延伸觀察：ChatGPT 透過 MCP 讀取 Figma，與平台直接呼叫 Figma API 的整合方式不同，不能直接比較額度。
05
分析品質
AI 產出太少時，先確認規則，而不是要求更多
問題
分析一個大型、流程複雜的頁面，AI 卻只產出 8 筆埋點事件。直覺會想要求 AI「多產一點」。
決策
先回頭檢查整條資料流：Figma 資料有沒有讀完整、送給 AI 時有沒有被截斷、建議是否涵蓋主要流程，並請 Codex 列出目前的分析規則。
結果
確認平台的策略是「挑選有價值的第一階段事件」，而非「列出所有操作」，並找出輸入上限是大型頁面產出偏少的原因之一。
RESULT大型流程只產出 8 筆
CODEX · AI 模型主要限制
只根據本次選定 Page 的來源節點，不預設產業、不沿用其他專案。
去識別化，但保留功能語意。
排除返回、取消、關閉、部分收合、日期導覽及純資訊顯示；後端也會過濾。
只保留有產品決策價值的事件，允許零筆，最多 80 筆。
輸入摘要上限為 1,200 節點、96,000 字元，大型頁面不保證每個節點都送進模型。
05 / Process

與 AI 協作的五個階段

不是一次下指令就完成，而是透過需求定義、功能驗證與反覆修正，逐步把產品做出來。

01
ChatGPT
定義需求與規格

釐清需求、使用流程與功能規格，建立開發依據。

02
Codex
建立產品初版

開發核心功能，實際操作並檢查流程是否符合預期。

03
Figma / OpenAI / Gemini
串接 Figma 與 AI

取得設計資料，讓 AI 分析畫面並產生埋點建議。

04
GitHub × Cloudflare
部署網站

以 GitHub 管理程式碼，透過 Cloudflare 部署正式網站。

05
Codex
測試與持續優化

處理授權、API 額度與操作中的異常狀況。

我和 AI 協作的方法
分開「規則」與「範例」

需求裡只寫產品通用的規則，特定專案當作測試資料，避免 AI 把範例當成預設。

追問資料從哪裡來

不因為介面有結果就當作完成，持續確認流程是否真的有執行、資料是否完整。

用結構化方式回報問題

比起「這裡不好用」，明確描述情境，Codex 才能逐項修正、再驗收。

回報方式：
操作步驟實際結果預期結果請 Codex 修正
部署選擇：Vercel 還是 Cloudflare？
比較Vercel像「前端專屬的精品工作室」Cloudflare像「全球物流網＋自家倉庫」
最大優點每次改動自動產生預覽連結程式在離使用者最近的機房執行
資料與儲存透過市集串接其他廠商服務資料庫、儲存、快取都是自家服務
適合誰重視開發順手、快速預覽的團隊想一個平台包辦網站、後端與資料
對我的專案要重新確認架構相容、再測一次Codex 已照 Cloudflare 規格建好，直接沿用
DEPLOY連接 GitHub 後自動建置與部署

07 / Reflection

技術門檻降低後，
「體驗」反而更有價值。

AI 補上了技術，但哪些問題值得解決、怎樣才算好用，仍需要設計師的判斷與經驗。

我學到的事
API 與資料流

理解 Figma 資料如何被讀取、整理，再交給 AI 分析，而不只是看到最後的結果。

OAuth 與權限

理解 PAT 與 OAuth 的差異，以及授權成功不代表 API 就能無限制使用。

部署與環境

理解 GitHub 與 Cloudflare 的角色；程式寫好，不代表網站已經能用。

避免重複讀取資料

同一份設計稿不必每次重新讀取，也要判斷資料何時該更新、何時已過期。

下一步
讓快取機制正式上線

把讀取與分析分開的優化方向落地，降低 API 額度消耗。

完成 Figma App 審核

通過官方審核後，讓更多團隊不需額外設定就能使用。

驗證實際成效

導入團隊後，追蹤規劃時間、採用率與工程端回饋，用數據驗證產品價值。
